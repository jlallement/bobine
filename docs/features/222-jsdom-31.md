- **Statut** : fait
- **Dépend de** : 206, 210, 218
- **Agents** : les deux (outil d'essai seulement, rien n'est livré).

## Pourquoi

Dependabot propose jsdom 31.0.0 (PR jlallement/bobine#10). Sa CI échoue sur trois essais du
pilote, « clic par libellé (fiche 210) ». Le pilote tourne en production contre la vraie page
Chromium d'Electron ; jsdom n'est que le banc d'essai : il faut savoir si jsdom 31 a changé un
comportement dont dépendent les essais, ou s'il révèle un vrai défaut du code du pilote.

## Critères d'acceptation

- [x] jsdom en `^31.0.0` (dernière 31.x publiée), dépendance de développement seulement.
- [x] Cause des trois échecs établie, preuve à l'appui.
- [x] Les essais du pilote et ceux de l'interface (`renderer`, environnement jsdom) passent,
  sans avertissement ni essai ignoré de plus qu'avec jsdom 30.
- [x] jsdom absent des avis de licence livrés (`scripts/third-party/inventory.json`).
- [x] `./scripts/verify` vert.

## Plan

`package.json` et `pnpm-lock.yaml` seulement, sauf si la cause est dans le code du pilote
(`scripts/pilote/actions.mjs`) ou dans son banc d'essai (`scripts/pilote/pilote.test.mjs`).

## Journal

- 2026-11-10 — **Cause : le fichier de verrouillage de Dependabot, pas jsdom ni le pilote.**
  Les trois essais échouent dans `new JSDOM(...)`, avant toute ligne du pilote :
  `TypeError: this.parser.tokenizer.flushCharacters is not a function`
  (`parse5-parser-stream/dist/index.js:60`, appelé par `jsdom/.../parser/html.js:437`).
  jsdom 31 analyse désormais tout document en flux (`parse5-parser-stream`) et appelle
  `flushCharacters()` après chaque morceau ; cette méthode du tokenizer n'existe que depuis
  parse5 8.1.0. Or `parse5-parser-stream@8.1.0` déclare `parse5: ^8.0.0` (corrigé en `^8.1.1`
  dans 8.1.1, publiée le 2026-11-07) : le verrou de Dependabot a gardé le `parse5@8.0.1` de
  jsdom 30 et l'a donné à `parse5-parser-stream@8.1.0`, à côté du `parse5@8.1.0` de jsdom.
  Reproduit à l'identique en local avec le verrou de la PR (`pnpm install --frozen-lockfile`) :
  les trois mêmes échecs.
- 2026-11-10 — **Dégât plus large que les trois essais annoncés.** Avec ce verrou, les
  119 fichiers d'essai du projet `renderer` (environnement jsdom de vitest) ne démarrent même
  pas (« Failed to start forks worker », même `TypeError`) : 0 essai joué, 119 erreurs. La CI de
  la PR le montre aussi (« Unhandled Errors ») ; seuls les trois essais du pilote apparaissaient
  comme « échoués », d'où l'impression que le reste passait.
- 2026-11-10 — **Correctif : verrou régénéré par pnpm** (`pnpm add -D jsdom@^31`) : un seul
  `parse5@8.1.1`, `parse5-parser-stream@8.1.1`. Aucun changement du code du pilote ni de ses
  essais : le clic par libellé se comporte pareil sous jsdom 31 (29/29 essais du pilote). Pas
  d'`overrides` pnpm pour forcer `parse5-parser-stream` : le verrou suffit (CI en
  `--frozen-lockfile`), et un verrou de ce genre ferait de nouveau échouer tout `renderer`,
  donc impossible à manquer.
- 2026-11-10 — Notes de version de jsdom 31 lues : moteur CSS remplacé (styles calculés),
  analyse qui peut s'arrêter sur un script bloquant (le constructeur peut rendre un document
  partiel), canvas via `@napi-rs/canvas` (dépendance facultative, non installée). Rien ne touche
  nos essais : `renderer` donne 119 fichiers / 746 essais passés avec jsdom 30.1.3 comme avec
  31.0.0, mêmes avertissements (deux, de Vite, sans rapport).
- 2026-11-10 — Licences : jsdom n'est pas dans `inventory.json` (outil de développement) ; la
  mention de parse5 dans `THIRD-PARTY-NOTICES.md` vient de la licence de Vite (ses dépendances
  embarquées), pas de jsdom. Pas d'e2e : aucun code de production touché.
