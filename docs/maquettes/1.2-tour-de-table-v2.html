Tour de table — maquettes finales

Version retenue le 2026-11-24, après la passe de simplification et les choix de l’utilisateur. Un tour de table se lance en deux gestes (/roundtable ou le bouton, puis Entrée) ; les participants se règlent une fois, dans un menu à cases. Une seule ligne grise dit le surcoût en jetons avant l’envoi ; le pied de la carte dit ce qui a été réellement consommé.

Exemple suivi : projet atelier (API Node + Postgres). La conversation tourne sur OpenCode · GPT-6.1 Sol, qui fait la synthèse ; les participants sont DeepSeek V4.1 Flash, GLM 5.3 Flash (OpenCode) et IBM Bob.

Surcoût Dans la ligne du tour de table, sous la question : « + synthèse · ≈ 4 fois les jetons d’une question simple », gris, une ligne ; même phrase à côté de la réplique
Après la synthèse Carte repliée en une ligne ; les avis restent à un clic
Synthèse Avis anonymisés pour le modèle qui synthétise (« Participant A, B, C », ordre mélangé) ; vrais noms dans l’interface

Synthèse et actions

Le modèle qui synthétise reçoit les avis sous « Participant A, B, C », dans un ordre mélangé ; l’interface redonne les vrais noms. Une action principale, appliquer ; une action secondaire, la réplique, avec son surcoût en gris.

Synthèse du tour de table · GPT-6.1 Sol

Ce que je rejette

  • Redis + BullMQ maintenant (Participant A) : une base de plus à superviser pour 0,25 tâche par seconde.
  • SQS (Participant CIBM Bob) : l’hébergement est chez Scaleway ; un second fournisseur pour une file.

Ce qui reste ouvert

  • À partir de quel volume repartir vers une file dédiée ? Proposé : au-delà de 50 tâches par seconde.

Ma recommandation

pg-boss, derrière une petite interface JobQueue. Archivage à 7 jours, alerte si une tâche attend plus de 2 minutes. Confiance haute.
