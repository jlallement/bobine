# ADR-0073 — Troisième ligne de publication : `v1.2.*` depuis la branche `1.2`

- **Statut** : accepté (décision de Jérôme, 2026-11-25)
- **Date** : 2026-11-25
- **Complète** : [ADR-0068](0068-preversions-ligne-suivante-depuis-sa-branche.md) (sans le
  modifier)
- **Fiches** : [218](../features/218-publication-preversion.md),
  [285](../features/285-tour-de-table.md) (tour de table, ADR-0072),
  [274](../features/274-avis-nouvelle-version.md) (avis de nouvelle version, ADR-0066)

## Contexte

La 1.2 (tour de table, fiche 285) se prépare sur la branche `1.2`, partie de `1.1` : elle reçoit
`1.1` (donc `main`) mais n'est jamais fusionnée dans `1.1` ni dans `main`. Jérôme veut publier
une première préversion **1.2.0-beta.1** depuis `1.2`, pendant que la 1.0 continue depuis `main`
et la 1.1 depuis `1.1`. La liste fermée de l'ADR-0068 (`v1.0.*` : `main`, `v1.1.*` : `1.1`)
refuse tout tag `v1.2.*`, et `ci.yml` ne tourne pas sur les poussées de `1.2`.

## Décision

1. **Troisième ligne, liste toujours fermée.** Le job `guard` de `release.yml` accepte un tag
   `v1.2.*` dont le commit est sur `origin/1.2`. Toute autre ligne reste refusée.
2. **CI sur `1.2`.** `ci.yml` tourne aussi sur les poussées de `1.2` (`main`, `1.1`, `1.2`, et
   aucune autre branche), pour que le `guard` trouve `verify` vert sur les trois systèmes.
3. **Le reste de l'ADR-0068 s'applique tel quel** : tag = version de `package.json`, préversion
   jamais « Latest », notes tirées des deux changelogs du commit tagué.

## Alternatives écartées

- **Une règle ouverte (`v1.N.*` depuis la branche `1.N`)** — une branche nommée `1.3` par
  erreur publierait sans décision ; l'ADR-0068 veut une liste fermée.
- **Attendre que `1.1` soit fusionnée dans `main`** — retarde les essais du tour de table par
  des testeurs, sans rien gagner en sûreté.

## Conséquences

- Trois lignes publiées en parallèle : `main` (1.0), `1.1`, `1.2`. Chaque branche de ligne
  plus récente reçoit la précédente ; aucune n'est fusionnée dans une plus ancienne.
- Un tag lance le `release.yml` **du commit tagué** et une poussée de `1.2` lance le `ci.yml` de
  `1.2` : ces changements doivent être dans `1.2` avant le premier tag `v1.2.*`. Le reste du
  chemin (version dans `package.json`, changelogs, poussée de `1.2`, puis tag) est celui de la
  fiche 218.
- Un tag `v1.2.*` posé sur un commit de `1.1` ou de `main` passe la règle de branche (ancêtres de
  `1.2`), mais pas celle de la version (`package.json` en 1.1.x ou 1.0.x).
- Avis de nouvelle version (ADR-0066, `src/shared/update-check.ts`) : aucun changement de code.
  Constaté avec `pickUpdate` sur une liste qui mêle 1.0.x, 1.1.x et 1.2.0-beta.N : une 1.1.x
  finale ne voit jamais une préversion ; une 1.1.0-rc.N ne voit pas la 1.2.0-beta.1 (autre
  majeure.mineure) ; une 1.2.0-beta.1 voit la 1.2.0-beta.2 et la 1.2.0 finale, jamais une 1.1.x
  ni une 1.0.x (plus anciennes). Une finale plus récente d'une autre ligne (1.1.1 pour une
  1.0.1) reste proposée, comme avant.
- « Latest » : mêmes réserves que l'ADR-0068 ; une préversion 1.2 ne l'est jamais.
- Réglages GitHub (propriétaire) : si un ruleset protège `main` et `1.1`, protéger `1.2` de la
  même façon.
